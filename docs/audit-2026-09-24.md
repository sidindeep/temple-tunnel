## Исходные дефекты Windows

Исходные идентификаторы A2/A4/A5/A7 сохранены для связи с доказательствами.

### A2 · P1 · Windows: применение настроек отменяет ручное отключение

**Код:** [src/main.js](../src/main.js#L2113), строки 83–90, 2058, 2113–2114. Аналогичный шаблон есть в обработчиках
списков приложений и `selectSubscription()` на строках 1690–1701.

Обработчик запоминает, что VPN работает, затем ожидает `saveState()` и запускает
туннель по сохранённому флагу. Если во время сохранения нажать «Отключить»,
позднее продолжение всё равно вызовет `startTunnel()`. Счётчик ручной отмены,
уже используемый обновлением ядер, здесь не проверяется.

**Доказательство:** текущий `settings:update` с задержанным сохранением:
смена режима → `manualDisconnect()` → `disconnected` → завершение сохранения
→ `connected`. Воспроизведено через существующий lifecycle harness с имитацией ядер.

**Правка:** связывать все отложенные действия, способные запустить VPN, с
поколением пользовательского намерения; после каждого ожидания проверять,
что ручная остановка не отменила это намерение. Сохранение настроек может
завершиться, но запуск после отмены запрещён.

**Готово, когда:** отключение во время сохранения режима, маршрутов, списка
приложений или смены подписки оставляет VPN отключённым. Регрессионные тесты
должны задерживать сохранение и проверять отсутствие позднего старта.

### A4 · P2 · Windows: удаление последней подписки оставляет session Kill switch

**Код:** [src/main.js](../src/main.js#L1676), строки 1676–1679; сравнить с `manualDisconnect()` на строках 83–89.

При удалении последней активной подписки работающий VPN останавливается через
`stopTunnel()`, который не снимает session-защиту. Для нормальной ручной
остановки эта очистка находится в другом методе.

**Доказательство:** удаление последней подписки при `killSwitch=session` даёт
`status=disconnected`, но `guardActive=true`. Проба использовала текущий
обработчик удаления и имитацию WFP. Реальная блокировка пакетов не измерялась.

**Правка:** направить намеренную остановку при удалении через общий контракт
ручного отключения. Сохранить отдельное поведение `always` и защиту при аварии.

**Готово, когда:** удаление последней подписки очищает session-фильтры,
сохраняет always-фильтры и корректно показывает ошибку, если очистка не удалась.

### A5 · P2 · Windows: повреждённое хранилище выглядит как пустое

**Код:** [src/main.js](../src/main.js#L204), строки 204–211, 213–272, 275–317, 421–424.

Ошибка расшифровки заменяется fallback. Для подписок это пустой список,
который затем кэшируется. Добавление новой подписки заменяет исходный
`subscriptionsEncrypted`, не сообщая о невозможности прочитать прежние данные.
Для повреждённого JSON загрузка также ограничивается записью в консоль.
Резервной копии перед последующим сохранением нет. Дополнительно ветка
`EEXIST/EPERM` в `saveState()` заменяет атомарный rename прямой перезаписью.

**Доказательство:** синтетическая ошибка DPAPI → `subscriptions()` возвращает
`[]` → добавление новой записи заменяет исходный ciphertext. На момент аудита
это оставалось проблемой, отмеченной в ревью 22 сентября.

**Правка:** различать отсутствие файла, повреждение JSON и ошибку расшифровки;
сохранять исходные байты, показывать состояние восстановления и запрещать
автоматическую перезапись. Добавить безопасную резервную копию и устойчивую
стратегию атомарной записи на Windows. Не сбрасывать пользовательские данные
без явного действия пользователя.

**Готово, когда:** обрезанный JSON, ошибка DPAPI, отказ rename и обрыв записи не
теряют последнюю читаемую копию и не маскируются под первую установку.

### A7 · P2 · Windows: VLESS с IPv6-адресом ошибочно отправляется в DNS

**Код:** [src/subscription.js](../src/subscription.js#L95), строки 65–68, 95, 119–120;
[src/server-probe.js](../src/server-probe.js#L17), строки 17–26.

VLESS сохраняет `URL.hostname` вместе с квадратными скобками. Для
`[2001:db8::1]` `net.isIP()` возвращает 0, и `resolveServer()` пытается выполнить
DNS-поиск вместо использования IPv6-литерала. Проверка loopback также пропускает
`[::1]`. Hysteria 2 уже удаляет скобки в своём парсере.

**Доказательство:** вызов действующих парсера и resolver с синтетическим lookup
показал запрос имени `[2001:db8::1]`; `[::1]` принят парсером. Внешние DNS-запросы
для воспроизведения не выполнялись.

**Правка:** нормализовать IP-литералы единообразно до проверки адреса,
формирования SNI и передачи VPN-ядру.

**Готово, когда:** обычный IPv6 проходит без DNS, loopback отклоняется,
IPv4/домены продолжают работать; соединение к тестовому IPv6-серверу проверено.

### A1 · P1 · Android: проверка соединения удаляет блокировку IPv6

**Код:** [SingBoxConfigBuilder.kt](../android/app/src/main/java/local/templetunnel/android/vpn/SingBoxConfigBuilder.kt#L52), строки 22, 52;
[TempleVpnService.kt](../android/app/src/main/java/local/templetunnel/android/vpn/TempleVpnService.kt#L89), строки 89–90.

При выключенном IPv6 первым создаётся правило `reject` для `ip_version: 6`.
Затем `rules.put(0, healthRule)` заменяет его правилом проверочного SOCKS-входа.
Сервис передаёт ненулевой `healthPort`, поэтому проблема относится к обычному
запуску VPN. При включённом IPv6 вместо этого теряется первое правило `sniff`.
Семантика замены, а не вставки, определена в
[документации JSONArray.put](https://developer.android.com/reference/org/json/JSONArray#put(int,%20java.lang.Object)).

**Последствие:** выключатель IPv6 перестаёт обеспечивать заявленную блокировку;
IPv6-пакеты могут обрабатываться последующими прямыми/прокси-маршрутами.
`ipv4_only` у DNS не блокирует соединения к готовым IPv6-адресам. Фактический
путь пакетов на устройстве не измерялся.

**Правка:** собирать упорядоченный список правил с проверочными правилами в
начале, сохраняя остальные элементы. Ограничить IPv6-блокировку входом TUN.

**Готово, когда:** при `healthPort > 0` и выключенном IPv6 в конфигурации остаётся
IPv6 reject; при включённом IPv6 остаётся sniff. Покрыть оба случая тестами
содержимого конфигурации и проверить IPv6-литерал на устройстве. Текущий JVM-тест
использует `healthPort = 0`; native `checkConfig` проверяет допустимость JSON,
но не наличие нужной политики.

### A3 · P1 · Android: устаревшая операция может закрыть новый туннель

**Код:** [TempleVpnService.kt](../android/app/src/main/java/local/templetunnel/android/vpn/TempleVpnService.kt#L68), строки 57–70, 94–100, 184–204.

Каждый reconnect создаёт отдельный `Thread`. В начале `startTunnel(ticket)`
сначала вызывается общий `stopCore()`, и лишь затем проверяется актуальность
ticket. Если старый поток получает управление после того, как новый уже
поместил своё ядро в `commandServer`, старый поток закрывает новое ядро,
после чего обнаруживает отмену. `coreLock` защищает присваивание ссылок, но не
принадлежность ресурсов операции. Устаревшая ошибка затем игнорируется;
возможны разрыв нового подключения и несогласованный статус UI.

**Правка:** сериализовать lifecycle на одном исполнителе либо coroutine actor;
связать ядро, TUN и публикацию статуса с конкретным поколением. Проверять отмену
до изменения ресурсов и закрывать только ресурсы своей операции. Аналогично
защитить отложенную остановку; для завершения сервиса учитывать `startId`,
как предусмотрено [контрактом Android Service](https://developer.android.com/reference/android/app/Service#stopSelfResult(int)).

**Готово, когда:** управляемое чередование двух reconnect и disconnect не
позволяет старой операции закрыть новое ядро, открыть поздний TUN или выставить
поздний статус. После этого проверить быстрые изменения маршрутов и смену сети
на устройстве. Сейчас вывод основан на порядке операций в исходнике.

### A6 · P2 · Android: поздний ответ старой подписки меняет новый выбор

**Код:** [MainViewModel.kt](../android/app/src/main/java/local/templetunnel/android/MainViewModel.kt#L48), строки 48–56, 86–100;
[MainActivity.kt](../android/app/src/main/java/local/templetunnel/android/MainActivity.kt#L154), строки 154–162.

`refreshSubscription()` запоминает подписку A, ждёт сеть и затем без проверки
активной подписки меняет глобальный `selectedServerId` по серверам A. Пока идёт
запрос, пользователь может выбрать B: `busy` не блокирует этот выбор. Аналогично
ведёт себя завершение `measureServers()` при автоматическом выборе.

**Последствие:** активна B, но выбранный ID относится к A; UI/сервис переходят
к запасному выбору первого сервера B и могут перезапустить соединение вопреки
последнему выбору пользователя. Подтверждено анализом кода, без запуска на Android.

**Правка:** обновлять список/замеры по идентификатору и версии исходной подписки;
менять активный сервер только при сохранении того же пользовательского выбора.
Хранить выбранный сервер отдельно для каждой подписки либо обеспечить эквивалентный
инвариант. Не применять результаты удалённой или изменённой подписки.

**Готово, когда:** сценарии «обновление/замер A → выбор B → ответ A», удаление A
и ручной выбор сервера во время замера сохраняют актуальную подписку и сервер.

### A8 · P2 · Android: ошибка защищённого хранилища приводит к необработанному исключению

**Код:** [MainViewModel.kt](../android/app/src/main/java/local/templetunnel/android/MainViewModel.kt#L34), строки 33–34, 84, 122–126;
[TempleRepository.kt](../android/app/src/main/java/local/templetunnel/android/data/TempleRepository.kt#L15), строки 15–28.

Repository теперь корректно не подменяет ошибку чтения пустыми данными, но
создание ViewModel вызывает `repository.load()` без обработки ошибки. Вызовы
сохранения из переключателей также находятся вне `work()` и его обработчика.
Ошибка Keystore, расшифровки/JSON или неудачный `commit()` распространяется в UI
вместо предусмотренного сообщения о восстановлении. Проверено по исходнику;
сбой на устройстве не инъецировался.

**Правка:** ввести явное состояние недоступного хранилища, перехватывать ошибки
инициализации и записи на границе UI, сохранять исходные данные и не принимать
изменения как успешно записанные. Выносить синхронное дисковое сохранение с UI-потока.

**Готово, когда:** тесты с ошибками чтения/записи сохраняют работоспособный экран
с понятной ошибкой и безопасным повтором; автоматического удаления данных нет.
